## 1) 이 문서가 다루는 것

이 폴더에는 멤버·졸업생 프로필을 보여 주는 컴포넌트가 모여 있다. 이 문서는 그중 다른 페이지에서 사람 이름에 띄우는 호버 카드(`ProfileHoverLink.tsx`)만 다룬다. 카드 목록, 상세 화면 같은 나머지 파일은 아직 적지 않았다.

논문·특허와 프로젝트의 호버 카드는 `src/components/Publication/README.md`, `src/components/Research/README.md`에 있다.

## 2) ProfileHoverLink.tsx

| 항목 | 내용 |
| --- | --- |
| 내보내는 것 | `ProfileHoverLink`, `ProfileAuthorName` |
| 받는 값 | `profile` (`getProfileLinks()`가 만든 사전에서 꺼낸 한 사람의 값), `className`, `children` (링크 글자) |
| 쓰는 곳 | 논문·특허 목록(`Publication/PaperList.tsx`, `Publication/PatentList.tsx`), 뉴스 목록(`Board/NewsList.tsx`), 세미나 목록(`Board/SeminarList.tsx`), 스터디(`Study/index.tsx`), 프로젝트 목록(`Research/ProjectList.tsx`), 프로필 상세(`ProfileDetailPaper.tsx`, `ProfileDetailPatent.tsx`) |

- 클릭하면 그 사람의 프로필 페이지로 이동한다.
- 카드를 띄우고 위치를 잡는 동작은 공용 컴포넌트 `src/components/HoverCardLink.tsx`가 맡는다. 이 파일은 카드 안의 내용만 그린다.
- 호버가 없는 터치 기기에서는 카드 없이 링크로만 동작한다.
- `ProfileAuthorName`은 저자 이름용이다. 프로필이 있는 사람은 링크와 호버 카드로, 없는 사람은 글자로만 그린다.

카드에 나오는 내용은 다음과 같다.

| 자리 | 내용 |
| --- | --- |
| 왼쪽 사진 | 대표 사진(프로필 `photo`의 첫 장). 96×118px 칸 |
| 첫 줄 | 영문 이름 |
| 둘째 줄 | 한글 이름. 없으면 줄이 빠짐 |
| 셋째 줄 | 직함. 예: Ph.D. Student (3학기) |
| 마지막 줄 | 소속, 입학, 참여 기간 중 한 줄. 최대 두 줄까지 보이고 넘치면 잘림 |

### 2-1) 카드 값을 만드는 시점

호버할 때 만드는 것이 아니라 페이지를 그릴 때 미리 만든다. 호버는 만들어 둔 값을 보여 주기만 한다.

- 서버 페이지가 `getProfileLinks()` (`src/data/loaders/index.ts`)를 호출해 전체 사람의 카드 값을 사전 하나로 만든다. 사전의 키는 프로필 YAML의 `id`다.
- 각 컴포넌트는 이 사전에서 ID로 한 사람의 값을 꺼내 `ProfileHoverLink`에 넘긴다.
- 값에는 이름, 직함, 한 줄 소개와 함께 사진의 **주소**가 들어 있다. 사진 파일 자체는 들어 있지 않다.
- 정적 페이지는 프로필 YAML을 고쳐도 페이지가 다시 그려져야 카드에 반영된다. 다시 그려지는 조건은 `src/data/README.md`의 3)을 참고한다.

### 2-2) 사진 파일을 받는 시점

카드 값은 미리 만들어 두지만, 사진 파일은 **처음 포인터를 올릴 때** 받는다. 개발자 도구의 Network 탭에서 호버하는 순간에 이미지 요청이 뜨는 것은 정상이다.

브라우저는 화면에 `<img>`가 생길 때 그 파일을 받는다. `HoverCardLink.tsx`는 카드가 열려 있을 때만 카드를 화면에 추가하므로, 카드 안의 `<img>`도 그때 처음 생긴다.

| 시점 | 일어나는 일 |
| --- | --- |
| 페이지를 그릴 때 | 카드 값과 사진 주소를 만들어 페이지에 넣어 둠 |
| 페이지를 열 때 | 값만 받음. 사진 요청 없음 |
| 처음 포인터를 올릴 때 | 0.28초 뒤 카드가 열리면서 사진을 받음 |
| 같은 사람에 다시 올릴 때 | 브라우저 캐시에서 바로 표시. 새 요청 없음 |

- 사진을 미리 받지 않는 것은 의도한 동작이다. 뉴스나 논문 목록에는 이름이 많이 나오는데, 미리 받으면 방문자가 올려 보지 않을 사진까지 전부 받게 된다.
- 같은 사진이 그 페이지에 이미 떠 있으면(예: 멤버 페이지) 호버해도 새 요청이 생기지 않을 수 있다.
- 키보드로 링크에 포커스가 가면 지연 없이 바로 열린다.

### 2-3) 사진을 2배 파일 하나로 고정한 이유

카드 사진은 `next/image`의 `<Image>`가 아니라 일반 `<img>`로 그리고, 주소는 칸 폭 96px의 2배(192px)에 해당하는 파일 하나만 넣는다. 후보 목록(`srcset`)은 넣지 않는다.

- `<Image>`는 한 사진에 여러 폭의 후보를 붙여 브라우저가 고르게 한다. 크롬은 그중 더 큰 파일이 이미 받아져 있으면 새로 받지 않고 그것을 쓴다.
- 멤버 페이지처럼 같은 사진의 300~640px 변환본이 이미 받아져 있는 곳에서, 그 파일이 당시 88px이던 칸에 눌리면서 가장자리가 거칠고 날카롭게 보였다. Firefox에서는 일어나지 않았고, 품질 값과는 무관했다.
- 후보가 하나뿐이면 브라우저가 다른 크기로 바꿔 쓸 수 없다.
- 주소는 `getImageProps`에 `sizes` 없이 `width: 96`만 넘겨서 얻는다. 이렇게 하면 후보가 1배와 2배 두 개만 나오고, `src`가 그중 2배다. 2배 후보는 `images.imageSizes`에서 192 이상인 가장 작은 값이라, 목록에 192가 없으면 230px 파일이 된다.

알아 둘 점은 다음과 같다.

- 거칠어지는 조건은 칸에 비해 파일이 큰 것이다. 모니터를 네이티브 해상도로 둔 화면(배율이 낮은 화면)에서 같은 사진을 88px 칸(당시 크기)에 넣어 보면 176px 파일만 깨끗하고, 300px 이상은 전부 날카롭게 보였다(2026년 11월, 크롬에서 눈으로 확인).
- Vercel 변환을 거쳤는지, 품질이 q75, q82, q100 중 무엇인지는 관계없었다. `public`의 파일(WebP q82)을 그대로 넣어도 똑같이 날카로웠다.
- 배율이 높은 화면에서는 같은 파일이라도 덜 드러난다. 칸이 더 많은 픽셀로 그려져 브라우저가 줄이는 폭이 작아지기 때문이다.
- `next.config.mjs`의 `images.unoptimized`가 켜져 있는 동안에는 2배 파일이 아니라 `public`의 파일이 그대로 쓰이므로, 배율이 낮은 화면에서 카드 사진이 날카롭게 보인다.
- 사진 폭을 바꾸려면 `next.config.mjs`의 `images.imageSizes`에 그 값이 있어야 한다. 없으면 그보다 큰 가장 가까운 폭으로 바뀐다.

## 3) 데이터 흐름

1. 서버 페이지가 `getProfileLinks()`로 전체 사람의 카드 값 사전을 만든다 (`src/data/loaders`).
2. 페이지는 그 사전을 목록 컴포넌트(`PaperList`, `NewsList` 등)에 `profileLinks`로 넘긴다.
3. 목록 컴포넌트는 사람 ID로 사전에서 값을 꺼내 `ProfileHoverLink`에 넘긴다.
4. 포인터를 올리면 `HoverCardLink`가 카드를 열고, 그때 브라우저가 사진을 받는다.
