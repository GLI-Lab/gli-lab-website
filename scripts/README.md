## 1) 이 폴더가 하는 일

`public/`에 넣은 원본(한글 파일명, JPG/PNG, 큰 사진)을 사이트가 쓸 수 있는 형태로 바꾼다. 네 스크립트는 `package.json`의 `prebuild`가 아래 순서로 실행한다.

```
normalize-public-filenames.js
  → optimize-images.js
  → generate-og-images.js
  → generate-public-file-index.js
```

여기 스크립트는 **git에 올릴 원천 파일**을 웹용 크기로 맞춰 두는 단계다. 화면 칸에 맞춘 리사이즈는 지금 어디서도 하지 않는다. `next.config.mjs`의 `images.unoptimized`가 켜져 있어(Vercel 이미지 변환 한도 때문, 2026-11-16부터) 여기서 만든 파일이 그대로 나간다. 칸 크기에 맞는 파일을 미리 만드는 계획은 [8)](#8-칸별-파일-미리-만들기-계획)에 있다.

## 2) 실행 순서

```bash
$ pnpm prebuild
# 또는 하나만
$ node scripts/optimize-images.js
$ node scripts/generate-og-images.js          # 사진 해시가 바뀐 OG만 생성
$ node scripts/generate-og-images.js --force  # 전부 다시 생성
```

할 일이 없으면 각 스크립트는 건너뛰므로 반복 실행 비용은 작다. 새 멤버 사진을 넣은 뒤에는 `prebuild`를 돌리고 생성된 WebP·OG를 함께 커밋한다.

## 3) normalize-public-filenames.js

**목적:** `public/` 한글 파일명을 NFC(완성형)로 맞춘다.

macOS는 한글을 NFD(조합형)로 저장한다. 리눅스 서버에서는 같은 글자가 다른 파일명이 되어, 프로필 사진 정렬(`1`, `2`, `3`)이 깨질 수 있다. `public/pdf/seminar`, `public/pdf/cv`, `public/images/profiles`를 훑어 NFC가 아닌 이름만 바꾼다.

## 4) optimize-images.js

**목적:** 갤러리·프로필 사진을 WebP로 바꾸고, 긴 변이 한도를 넘으면 줄인다. JPG/PNG 원본은 변환 후 삭제한다.

한도는 **가로·세로 중 긴 변**이다. `fit: inside`로 그 상자에 비율을 유지한 채 넣는다. 세로 사진이면 세로가 한도, 가로는 더 짧다.

| | 긴 변 한도 | 품질 | 대상 |
|---|---|---|---|
| 갤러리 `public/images/gallery/<폴더>/` | 2048px | WebP q82 | JPG/PNG 변환. 이미 WebP이고 2048 이하면 스킵 |
| 프로필 `public/images/profiles/`, `.../alumni`, `public/images/etc` | 1600px | WebP q82 | JPG/PNG 변환. **이미 WebP여도 1600을 넘으면 리사이즈** |

한도 이유: 지금 화면(갤러리 모달 1024 CSS px, 프로필 상세 `sizes` 640px)보다 여유를 두어 레이아웃이 한 단계 커져도 레티나를 맞춘다. 갤러리 2048 = 모달 1024×2. 프로필 1600 = 상세보다 크고, 나중에 큰 모달을 켜도 버틴다. q82인 이유: 웹에서 눈으로 무손실에 가까운 구간이다.

이미 WebP이고 한도 이하면 건너뛴다. 갤러리 기존 WebP를 q82로 다시 누르지는 않는다.

```bash
$ node scripts/optimize-images.js
```

## 5) generate-og-images.js

**목적:** 프로필 공유용 Open Graph 이미지(1200×630 WebP)를 `public/images/profiles-og/`에 미리 만든다.

최신 `profiles.yaml` / `profiles-alumni.yaml`을 읽고, 사진·이름·역할을 합성한다. 최신 학기 파일은 `src/data/loaders/profileYamlFile.js`를 쓰며, 사이트 로더(`profileLoader.ts`)와 같다. 결과는 git에 커밋한다. 서버의 한글 폰트에 의존하지 않도록 빌드 산출물이 아니라 저장소에 둔다.

- 기본: `public-file-index.json`의 프로필 사진 해시와 지금 `*1` 파일을 비교한다. 이 스크립트가 인덱스보다 **먼저** 돌므로 JSON은 직전 배포의 해시이고, 같은 이름으로 사진을 갈아끼우면 달라져 OG를 다시 만든다.
- `--force`: 해시와 관계없이 전부 다시 생성. 이름·역할만 바꿨거나 OG 레이아웃을 바꿨을 때

```bash
$ node scripts/generate-og-images.js
$ node scripts/generate-og-images.js --force
```

## 6) generate-public-file-index.js

**목적:** `public/`을 런타임에 `readdir`하지 않도록, 파일명 목록과 프로필 사진 내용 해시(SHA-256 앞 8자)를 `src/data/generated/public-file-index.json`에 적는다.

로더가 이 JSON만 읽는다. 해시는 같은 파일명으로 사진을 갈아끼워도 `?v=`가 바뀌어 1년 캐시를 피하게 한다. 인덱스가 가리키는 폴더: `pdf/seminar`, `pdf/cv`, `images/profiles`. 갤러리·포스터는 YAML/폴더 구조가 달라 넣지 않는다.

`prebuild` 마지막에 실행된다. 사진을 지웠는데 인덱스를 안 돌리면 개발 서버(`next dev`는 prebuild를 안 탐)가 없는 파일을 가리킬 수 있다.

## 7) 사진 추가·삭제 후

1. 파일을 `public/images/profiles/` 또는 `public/images/gallery/<폴더>/`에 넣거나 지운다.
2. `pnpm prebuild` (또는 위 스크립트를 순서대로). 같은 이름 사진 교체도 OG가 다시 만들어진다.
3. 생성된 WebP·OG·`public-file-index.json`을 커밋한다.

## 8) 칸별 파일 미리 만들기 (계획)

> **계획이다. 아직 구현하지 않았다** (2026-11-16 기준). 아래 폴더, 파일, 스크립트 단계는 지금 저장소에 없다. 구현하면 이 절을 "현재 동작"으로 고쳐 쓴다.

**목적:** 화면의 각 칸에 맞는 크기의 파일을 미리 만들어, 방문자가 받는 사진 용량을 줄인다.

지금은 `public`의 파일이 칸 크기와 관계없이 그대로 나간다. 폭 400px 남짓한 갤러리 카드에도 2048px 사진이 들어간다. 지금 설정에서 페이지를 열고 끝까지 내렸을 때 받는 사진 용량은 다음과 같다 (개발 서버, 1440px 창, 배율 100%).

| 페이지 | 지금 | 칸별 파일로 바꾸면 (추정) |
|---|---|---|
| 멤버 | 23장, 2.05MB | 약 0.4MB |
| 갤러리 | 98장, 23.7MB | 약 6MB |

- 목적은 화질이 아니라 용량이다. 지금 상태로도 사진이 깨지거나 거칠어 보이지는 않는다.
- Vercel 이미지 변환은 쓰지 않는다. 월 변환 한도와 무관한 구조다.

원칙은 **칸마다 "가장 큰 칸의 2배" 파일 한 장**이다.

- 배율 100% 화면에서는 브라우저가 절반으로 줄여 그리고, 200% 화면에서는 그대로 맞는다.
- 후보를 여러 개 주는 `srcset`, `sizes`는 쓰지 않는다. 화면 폭에 따라 칸이 달라져도 같은 파일을 브라우저가 칸에 맞춰 그린다.
- 네이버 메인이 이 방식이다. 이미지에 `srcset` 없이 칸의 정확히 2배 파일을 쓴다 (2026-11-16 확인).

### 8-1) 칸별로 필요한 해상도

칸 크기는 CSS px이고, 화면 폭에 따라 달라지는 칸은 전부 적었다.

| 칸 | 칸 크기 | 그리는 곳 | 들어가는 사진 | 쓸 파일 |
|---|---|---|---|---|
| 툴팁 사진 | 96×118 | `Profile/ProfileHoverLink.tsx` | 프로필 첫 사진 | 192px |
| 멤버 카드 | 115×135, 140×160, 150×170 | `Profile/ProfileCardItem.tsx` | 프로필 첫 사진 | 300px |
| 프로필 목록 | 280×330, 250×300 | `Profile/ProfileListItem.tsx` | 프로필 사진 전체 | 640px (상세와 공유) |
| 프로필 상세 | 280×330, 320×400 | `Profile/ProfileCardDetail.tsx` | 프로필 사진 전체, `images/etc` 3장 | 640px |
| 갤러리 모달 썸네일 | 64×64, 80×80 | `Gallery/GalleryModal.tsx` | 갤러리 사진 전체 | 짧은 변 160px |
| 갤러리 카드 | 폭 약 310~475 (휴대폰은 화면 폭) | `Gallery/GalleryItem.tsx` | 갤러리 사진 전체 | 800px |
| 갤러리 모달 큰 사진 | 최대 1024×768 | `Gallery/GalleryModal.tsx` | 갤러리 사진 전체 | 지금 `public` 파일 그대로 (2048px) |
| 헤더 로고 | 40~70 정사각 | `Header.tsx` | 로고 PNG 2개 | 140px |
| 푸터 로고 | 높이 36~64 | `Footer.tsx` | 로고 JPG 2개 | 높이 128px |
| 프로젝트 로고 | 폭 140~225 | `Research/ProjectList.tsx` | 기관 로고 9개 | 각자 표시 폭의 2배 (280~450px) |
| 메인 커버 배경 | 화면 전체 폭 | `Covers.tsx` | 4장 (1750~1920px) | 지금 파일 그대로 |

- 갤러리 모달 큰 사진은 새로 만들지 않는다. 4)의 한도 2048px이 이미 가장 큰 칸(1024px)의 2배다.
- 메인 커버는 화면 전체 폭에 깔리는 배경이라 지금 크기가 맞다.
- 갤러리 카드의 폭은 격자 설정에서 계산한 값이다. 화면에서 재지 않았다.
- 프로필 목록과 상세가 640px 한 장을 같이 쓴다. 280px 칸에서는 2배를 조금 넘는데, 배율 100% 화면에서는 560px 파일과 구분되지 않았고 200% 화면에서 약간 흐렸다. 파일 종류를 줄이는 쪽을 택했다.

### 8-2) 미리 만드는 파일

원본 수는 2026-11-16 기준이다.

| 원본 | 원본 수 | 만드는 것 | 새 파일 수 | 추정 용량 |
|---|---|---|---|---|
| 프로필 첫 사진 (`*1.webp`, 기본 사진 포함) | 32 | 툴팁 192px, 카드 300px | 64 | 약 0.7MB |
| 프로필 사진 전체 | 58 | 목록·상세 640px | 58 | 약 3MB |
| `images/etc` 사진 | 3 | 상세 640px | 3 | 약 0.2MB |
| 갤러리 사진 | 160 | 썸네일 160px, 카드 800px | 320 | 약 12MB |
| 헤더·푸터 로고 | 4 | 각 1개 | 4 | 0.1MB 미만 |
| 프로젝트 로고 | 9 | 각 1개 | 9 | 0.2MB 미만 |
| **합계** | | | **458** | **약 16MB** |

- 용량은 추정이다. 같은 방식으로 만들어 본 파일 몇 개의 크기에서 어림했다.
- 원본이 목표보다 작으면 키우지 않고 원본 크기로 둔다. 프로필은 640px보다 좁은 것이 15장, 300px보다 좁은 것이 1장이다.

### 8-3) 만드는 방법

1. **`optimize-images.js`에 "칸별 파일 만들기" 단계를 추가한다.** 4)의 변환이 끝난 `public` 파일을 읽어 8-1)의 크기로 줄여 저장한다.
2. **"칸의 2배를 덮는 크기"로 줄인다.** 폭만 맞추지 않는다. 툴팁은 192×236, 카드는 300×340, 목록·상세는 640×800을 덮게 한다. 폭만 맞추면 칸보다 가로로 넓은 사진이 200% 화면에서 확대되어 흐려진다.
3. **사진은 WebP q82로 저장한다.** 로고는 PNG, JPG 형식을 유지한다.
4. **원래 폴더와 섞지 않고 따로 둔다.** 예: `public/images/_sized/profile-card/<파일명>.webp`, `public/images/_sized/gallery-card/<폴더>/<파일명>.webp`. 프로필과 갤러리 폴더는 로더와 다른 스크립트가 파일 목록을 읽으므로, 그 안에 하위 폴더를 만들지 않는다. 폴더 이름은 정해진 것이 아니라 안이다.
5. **이미 있고 원본보다 새 파일이면 건너뛴다.** 다른 스크립트와 같이 반복 실행 비용을 작게 둔다.
6. **컴포넌트가 그 주소를 직접 쓰게 바꾼다.** 사진 주소와 칸 이름을 받아 칸별 파일 주소를 돌려주는 함수를 하나 둔다. 각 컴포넌트의 `quality`, `sizes` 속성과 `src/lib/preloadImages.ts`의 후보 고르는 코드는 지운다. 프로필 사진의 `?v=` 값은 그대로 붙인다.
7. **`next.config.mjs`의 `images.unoptimized`는 켜 둔다.**

품질을 q82로 둔 근거는 다음과 같다. 카메라 원본 20장에서 640×800 파일을 바로 만들어 비교했다.

| 품질 | 용량 (중앙값) | 무손실 대비 PSNR |
|---|---|---|
| q82 | 50KB | 40.0dB |
| q85 | 58KB | 40.9dB |
| q90 | 80KB | 42.9dB |

- q82, q90, 무손실을 2배 확대해 나란히 봐도 구분되지 않았다 (사진 한 장으로 확인).
- 카메라 원본이 있으면 `public`의 q82 파일이 아니라 원본에서 바로 만드는 편이 낫다. 손실 단계가 한 번으로 줄어든다. 원본은 저장소에 없고 따로 보관한다.

### 8-4) 순서와 남은 결정

용량 효과가 큰 순서다. 앞의 것만 해도 된다.

1. 갤러리 카드(800px)와 썸네일(160px). 효과가 가장 크다.
2. 멤버 카드(300px).
3. 목록·상세(640px). 원본이 대부분 1280px 안팎이라 효과가 작다.
4. 툴팁(192px), 로고. 용량 효과는 거의 없다.

툴팁에 대해 알아 둘 점은 다음과 같다.

- 큰 파일이 툴팁 칸(측정 당시 88px)에 들어가면 크롬에서 가장자리가 거칠어진다는 측정이 있었다 (GPU 렌더링, 헤드리스 크롬 캡처를 확대해 비교).
- 실제 모니터에서는 `public` 파일을 그대로 넣어도 문제없이 보였다 (2026-11-16). 그래서 툴팁용 파일은 급하지 않다.
- 툴팁을 2배 파일 한 장으로 고정한 배경은 `src/components/Profile/README.md`의 2-3)에 있다.

아직 정하지 않은 것은 다음과 같다.

- **만든 파일을 git에 넣을지, 빌드 때 만들지.** git에 넣으면 저장소가 약 16MB 커진다. 빌드 때 만들면 저장소는 그대로지만 `prebuild`가 길어진다. 얼마나 길어지는지는 재지 않았다. OG 이미지를 git에 두는 이유(서버 한글 폰트)는 여기에 해당하지 않는다.
- **멤버 카드, 갤러리 카드, 로고의 보이는 모습.** 아직 화면에서 비교하지 않았다. 만든 뒤 지금 화면과 나란히 놓고 확인한다.
